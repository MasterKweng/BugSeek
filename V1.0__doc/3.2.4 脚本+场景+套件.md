
  一、共性分析

  1.1 执行层面的共性

  从文档设计可以看出，三个模块确实都需要执行测试脚本，区别仅在于粒度和执行逻辑：


  ┌──────────┬──────────────┬──────────────────────────┬────────────────────────────────┐
  │ 模块     │ 执行粒度     │ 执行逻辑                 │ 数据模型                       │
  ├──────────┼──────────────┼──────────────────────────┼────────────────────────────────┤
  │ 测试脚本 │ 单接口       │ 独立执行，无依赖         │ api_test_scripts                 │
  │ 场景组装 │ 多接口链路   │ 按依赖顺序执行，变量传递 │ api_scenarios + api_dependencies │
  │ 测试套件 │ 测试用例集合 │ 批量执行，支持串行/并行  │ test_suites                    │
  └──────────┴──────────────┴──────────────────────────┴────────────────────────────────┘

  1.2 执行引擎的共性需求

  无论哪个模块，都需要以下核心能力：
   - ✅ HTTP 请求发送
   - ✅ 环境配置管理（base_url, variables, headers）
   - ✅ 断言验证
   - ✅ 执行结果记录
   - ✅ 测试报告生成
   - ✅ 超时控制
   - ✅ 失败重试机制

  1.3 用户提到的关键点

  > 场景组装成功后的内容，是需要将对应的代码作为一个项目推送到 git 上，结合 Jenkins 来进行执行的

  这说明场景组装有两个阶段：
   1. 设计阶段：AI 分析依赖关系，生成场景配置（保存在数据库）
   2. 执行阶段：将场景配置转换为 pytest 代码，推送到 Git，Jenkins 执行

  二、架构设计建议

  2.1 核心设计思想

  将执行引擎抽离为独立模块，提供统一的执行能力，三个模块通过不同的编排方式调用：

   ┌─────────────────────────────────────────────────────┐
   │              统一测试执行引擎                          │
   │  (TestExecutionEngine)                              │
   │  - HTTP 请求                                        │
   │  - 断言验证                                         │
   │  - 环境配置                                         │
   │  - 结果记录                                         │
   │  - 报告生成                                         │
   └─────────────────────────────────────────────────────┘
              ↑              ↑              ↑
       ┌──────┘              │              └──────┐
       │                     │                      │
   ┌─────────┐         ┌─────────┐          ┌─────────┐
   │单接口   │         │场景组装 │          │测试套件 │
   │执行器   │         │执行器   │          │执行器   │
   └─────────┘         └─────────┘          └─────────┘

  2.2 执行模式分层

  根据执行复杂度和环境，建议分层设计：


  ┌─────────┬──────────────┬───────────────┬───────────────────────────┐
  │ 层级    │ 执行内容     │ 执行位置      │ 使用场景                  │
  ├─────────┼──────────────┼───────────────┼───────────────────────────┤
  │ Level 1 │ 单个接口脚本 │ 本地 API 服务 │ 快速验证、开发调试        │
  │ Level 2 │ 场景链路     │ 本地 API 服务 │ 业务流程验证              │
  │ Level 3 │ 测试套件     │ Jenkins       │ CI/CD、回归测试、质量门禁 │
  └─────────┴──────────────┴───────────────┴───────────────────────────┘

  关键设计点：
   - Level 1 & 2：直接调用后端执行接口，实时返回结果
   - Level 3：生成 pytest 代码 → 推送到 Git → Jenkins 执行

  2.3 数据模型关系设计

   api_test_scripts (测试脚本)
           ↑
           │ (1:N)
           │
   api_scenarios (场景) ───────┐
           ↑                      │
           │ (1:N)               │
           │                      │ (1:N)
   test_suites (测试套件) ──────┘

   执行关系：
   - test_scripts_execution → 单个脚本执行记录
   - scenario_execution → 场景执行记录（包含多个脚本执行）
   - suite_execution → 套件执行记录（包含多个场景/脚本执行）

  四、执行流程设计

  4.1 单接口/场景执行流程（本地）

   前端请求 → 后端执行引擎 → 直接执行 → 返回结果
                 ↓
            记录到数据库
                 ↓
            生成实时报告

  适用场景：
   - 单接口快速验证
   - 场景业务流程验证
   - 开发调试阶段

  4.2 测试套件执行流程（Jenkins）

   用户创建套件 → 后端生成 pytest 代码 → 推送到 Git
                                             ↓
                                       触发 Jenkins 构建
                                             ↓
                                       Jenkins 执行 pytest
                                             ↓
                                       生成 Allure 报告
                                             ↓
                                       回调后端更新状态

  适用场景：
   - CI/CD 集成
   - 全量回归测试
   - 质量门禁
   - 定时任务

  七、总结

  核心观点

   1. 执行引擎应该抽离：三个模块共享统一的执行引擎，只是编排逻辑不同
   2. 执行模式分层：
      - 单接口/场景 → 本地执行，实时返回
      - 测试套件 → 生成代码 → Git → Jenkins
   3. 场景组装的双重属性：
      - 设计态：保存在数据库，支持可视化编辑
      - 执行态：转换为 pytest 代码，推送到 Git，Jenkins 执行

  实施建议

   1. 第一阶段：实现统一的执行引擎，支持单接口和场景本地执行
   2. 第二阶段：实现代码生成器，将场景转换为 pytest 代码
   3. 第三阶段：集成 Git + Jenkins，实现测试套件的 CI/CD 流程
