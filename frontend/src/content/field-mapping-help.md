# 字段映射功能说明

## 1. 这个功能在做什么

字段映射用于分析接口字段和数据库字段之间的对应关系，帮助用户理解：

- 一个 API 字段最终来自哪张表、哪一列
- 当前映射是由规则、AI 还是运行期证据得出的
- 哪些字段可以直接自动应用，哪些字段更适合人工复核

系统不会只看字段名，而是会综合多类证据：

- 数据库结构信息
- SQL lineage
- code lineage
- runtime verification
- 历史确认结果
- AI 补充判断

最终结果会体现在建议列表中的候选字段、置信度、关系类型和决策来源上。

## 2. 哪些因素会影响最终结果

字段映射结果通常受下面几类因素影响：

### 2.1 数据基础是否完整

- 当前版本是否绑定了正确的数据库结构
- 当前版本是否绑定了有效的 execution / trace
- 项目是否配置了正确的代码仓库和 workspace root
- 项目是否配置了 ORM / Mapper 类型

如果这些基础信息不完整，系统可用证据会减少，候选字段数量和准确率都可能下降。

### 2.2 证据类开关是否开启

- 是否启用 SQL lineage
- 是否启用 code lineage
- 是否启用 runtime verification
- 是否运行前重建 lineage

这类开关决定系统是否使用更强的结构化证据。

### 2.3 AI 和策略是否保守

- 是否启用 AI
- AI threshold 多高
- 当前 evidence mode 是 conservative、balanced 还是 aggressive
- 项目是否配置了高风险字段策略

这类参数决定系统更偏向“稳妥”还是“覆盖更多候选”。

## 3. 字段映射页面参数说明

下面这些参数是本次运行时直接可调的参数。

## 4. Path 参数

### 作用

控制本次任务是否分析接口路径参数，例如 `/users/{id}` 中的 `id`。

### 开启后的影响

- 会把路径参数一起纳入字段映射候选
- 适合需要覆盖完整接口入参的场景

### 关闭后的影响

- 任务会跳过路径参数
- 结果会更聚焦 Query / Body

### 适合场景

- 开启：做全量字段治理
- 关闭：只关心业务请求体或查询参数

## 5. Query 参数

### 作用

控制本次任务是否分析查询参数，例如 `?status=1&page=2`。

### 开启后的影响

- 会生成 Query 参数的字段映射建议
- 对列表筛选类接口很重要

### 关闭后的影响

- 会跳过查询条件类字段
- 结果量会减少

## 6. Body 参数

### 作用

控制本次任务是否分析请求体字段。

### 开启后的影响

- 适合新增、编辑、批量提交等接口
- 通常这部分字段数量最多，对结果影响最大

### 关闭后的影响

- 请求体字段不会参与分析
- 更适合只看 GET 接口的场景

## 7. 是否启用 AI

### 作用

控制系统是否在低置信或歧义场景下使用 AI 进行补充判断。

### 开启后的影响

- 在规则证据不足时，可能补出更多候选
- 有助于提升覆盖率

### 关闭后的影响

- 结果更保守
- 更依赖 schema、lineage、runtime 等强证据

### 建议

- 首次接入或希望少误判时，可以先关闭或配合较高 threshold
- 证据较弱但又希望提高覆盖率时，可以开启

## 8. AI Threshold

### 作用

控制 AI 介入和接受结果时的阈值。

### 阈值较高时

- AI 更难触发或更难覆盖现有规则结果
- 结果更稳
- 误判风险更低

### 阈值较低时

- AI 更容易参与
- 可能提升覆盖率
- 也更需要人工复核

### 建议

- 高准确率优先：阈值偏高
- 快速摸底优先：阈值适当降低

## 9. 是否启用 SQL Lineage

### 作用

SQL lineage 会分析 SQL 中的列投影、别名、聚合、关联、CTE、子查询等结构，判断接口字段可能来自哪些数据库列。

### 开启后的影响

- 对复杂查询场景帮助很大
- 能显著提升 join、聚合、派生字段的可解释性
- 对报表、详情聚合接口尤其有效

### 关闭后的影响

- 系统无法利用 SQL 结构证据
- 更依赖字段名、历史反馈和 AI

### 什么时候收益最大

- 已绑定 execution / trace
- 已有可解析 SQL
- 当前接口有 join、聚合、别名、case when、CTE 等复杂查询

## 10. 是否启用 Code Lineage

### 作用

code lineage 会分析 DTO、VO、Assembler、Mapper、Builder、Bean copy 等代码组装链路，判断 API 字段如何从对象属性一路传到响应字段。

### 开启后的影响

- 对代码组装较重的项目很有价值
- 能提升字段名不完全一致时的识别能力
- 对 `BeanUtils.copyProperties`、builder、stream map 等场景有帮助

### 关闭后的影响

- 系统无法利用代码赋值链
- 更依赖 SQL 和 runtime 证据

### 什么时候收益最大

- 项目已配置 workspace root
- 代码仓库结构完整
- DTO / Assembler / Mapper 逻辑较多

## 11. 是否启用 Runtime Verification

### 作用

runtime verification 会结合 execution 里的响应值和数据库值做交叉校验，验证候选字段是否真的和运行结果匹配。

### 开启后的影响

- 对高风险字段帮助很大
- 能提升最终置信度的可靠性
- 可以更好地区分多个相似候选

### 关闭后的影响

- 系统只能依赖静态证据
- 对高风险字段会更保守

### 什么时候收益最大

- 已绑定有效 execution
- 响应和数据库值能稳定对应

## 12. Evidence Mode

### 作用

决定系统本次运行是偏保守、平衡还是偏激进。

### conservative

- 更保守
- 更少依赖 AI
- 更适合高风险字段较多的场景

### balanced

- 默认推荐
- 在准确率和覆盖率之间做平衡

### aggressive

- 更积极使用补充证据和 AI
- 适合前期摸底或想尽量拉高覆盖率的场景
- 需要配合人工复核

## 13. 运行前重建 Lineage

### 作用

在本次任务开始前，优先根据已绑定 execution 和代码 workspace 重新构建 lineage 资产。

### 开启后的影响

- 使用更新的 lineage 证据
- 有助于减少“配置已改但证据仍旧”的情况
- 运行时间通常会增加

### 关闭后的影响

- 会直接使用已有 lineage 资产
- 任务更快，但证据可能不是最新的

### 建议

- 项目刚同步代码、刚补 trace、刚换版本时建议开启
- 日常重复运行且资产已稳定时可关闭

## 14. 项目级配置会如何影响结果

这些配置通常在项目页维护，是长期配置，不需要每次运行都改。

## 15. 仓库地址 / 默认分支 / Workspace Root

### 作用

告诉系统去哪里找代码，以及从哪个目录开始做 code lineage 扫描。

### 影响

- 配置正确时，code lineage 更容易命中真实代码链路
- 配置错误时，可能完全扫不到有效代码证据

## 16. ORM / Mapper 类型

### 作用

帮助系统更好地识别 mapper XML、注解式 ORM、实体映射等结构。

### 影响

- 配置正确时，ORM lineage 识别会更稳定
- 配置不清晰时，字段映射仍可运行，但会损失一部分结构化证据

## 17. 业务字典 / 枚举字典

### 作用

帮助系统识别 `status / type / level / role / code / text` 等枚举或业务字段。

### 影响

- 能提升枚举字段、别名字段的判断质量
- 对 code 值和展示值不一致的场景尤其有帮助

## 18. 高风险字段策略

### 作用

定义哪些字段属于高风险字段，以及这些字段是否允许自动通过或 AI 覆盖。

### 影响

- 会直接影响自动通过比例
- 能有效压低高风险误判

## 19. 版本级配置会如何影响结果

这些配置通常在版本页维护，用于描述当前版本绑定了哪些资产。

## 20. 绑定 Schema Snapshot

### 作用

指定当前版本使用哪份数据库结构。

### 影响

- 结构越准确，候选列越准确
- schema 过旧时，结果可能偏离当前版本真实表结构

## 21. 绑定 Execution / Trace

### 作用

指定当前版本优先使用哪些运行记录作为 evidence 来源。

### 影响

- 直接影响 runtime verification 和 SQL lineage 的可用性
- 没有 execution 时，这两类证据收益会明显降低

## 22. 自动构建 Lineage

### 作用

控制当前版本是否默认在运行前刷新 lineage。

### 影响

- 资产更新更及时
- 但单次任务耗时可能增加

## 23. 推荐使用方式

### 方案一：追求高准确率

- 绑定正确 schema
- 绑定真实 execution
- 开启 SQL lineage
- 开启 code lineage
- 开启 runtime verification
- evidence mode 选 conservative 或 balanced
- AI threshold 适当提高

### 方案二：追求高覆盖率

- 开启 AI
- evidence mode 选 balanced 或 aggressive
- 开启 SQL lineage 和 code lineage
- 如有条件，开启运行前重建 lineage

### 方案三：首次接入项目

- 先补项目级仓库和 workspace 配置
- 补版本级 schema 和 execution 绑定
- 先用 balanced 跑一轮
- 再根据结果决定是否提高保守性或提高覆盖率

## 24. 常见问题

### 为什么候选字段很少

常见原因：

- schema 未绑定
- execution 未绑定
- workspace root 不正确
- SQL lineage / code lineage / runtime verification 被关闭

### 为什么 AI 没有触发

常见原因：

- 当前已有足够强的非 AI 证据
- evidence mode 较保守
- AI threshold 较高
- 当前字段属于高风险字段

### 为什么高风险字段没有自动通过

常见原因：

- 高风险策略要求人工审核
- 当前证据仍不足够强
- runtime verification 未提供足够验证信号

### 为什么开启 lineage 后结果提升不明显

常见原因：

- 当前版本没有有效 execution / trace
- workspace 配置不正确
- SQL 或代码结构不完整
- 当前接口本身比较简单，lineage 增益有限

## 25. 总结

字段映射不是单靠一个开关就能显著变好，而是依赖“项目配置、版本绑定、运行参数、证据质量”共同作用。

如果想让结果更稳定，建议优先保证：

- 项目级配置完整
- 版本级资产绑定正确
- SQL lineage、code lineage、runtime verification 能拿到真实证据

在这个基础上，再调整 AI 和 evidence mode，效果通常会更明显。
