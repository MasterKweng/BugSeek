# 字段映射未完成改动清单

本文档只保留当前仍未完成、但值得后续继续投入的事项。此前清单中的主链接线、runtime verification 接入、AI guardrail、高风险终审门禁、lineage 独立生成链、lineage 独立存储、自动抽取链和正式任务入口均已完成，因此不再重复列出。

## P1：能力继续做深

### 1. 提升 code / ORM 自动抽取的准确率与覆盖率

当前状态：

- 已支持扫描本地 workspace 中的 `.xml`、`.java`、`.kt`、`.py` 文件
- 已能抽取：
  - XML mapper 中的 `result/property -> column`
  - setter 赋值
  - 属性赋值
  - MapStruct 风格注解映射
- 但目前仍属于“最小可用版本”，对复杂工程形态的覆盖还不够

仍可继续增强：

- 支持更多 ORM / mapper 模式
- 增强跨方法赋值链、helper 方法包装链识别
- 更稳地识别多层 DTO / VO / assembler 链路
- 降低同名字段误匹配

目标：

- 提升 code lineage 的覆盖率和准确率
- 让自动抽取更接近真实项目代码形态

优先级：高

---

### 2. 提升 SQL lineage 对复杂 SQL 的解析能力

当前状态：

- 已支持常见 `SELECT`、alias、expression、join path
- 已能在执行期 SQL trace 分析后落库为 lineage edge
- 但对复杂 SQL 的覆盖仍有限

仍可继续增强：

- 子查询
- 多层嵌套 select
- union / union all
- case when 更细粒度列级来源
- 动态 SQL / 方言差异

目标：

- 提升 SQL lineage 在复杂查询场景下的可用性
- 减少复杂 SQL 下回退到弱证据的概率

优先级：高

---

## P2：工程化与治理

### 3. 给 lineage 资产构建补更完整的任务编排与增量策略

当前状态：

- 已有正式入口：
  - API：`/impact/lineage/build`
  - Celery：`build_lineage_assets`
  - Engine：`build_lineage_assets()`
- 但还没有形成更完整的增量构建策略

仍可继续增强：

- 按 definition / version / workspace 维度做增量扫描
- 对重复构建做去重或覆盖策略
- 增加构建统计、耗时、扫描文件数、命中率等指标
- 对失败文件保留审计信息

目标：

- 让 lineage 资产构建从“可调用”升级成“稳定可运营”

优先级：中

---

### 4. 完善 lineage 资产的查询与审计能力

当前状态：

- 已有独立表：
  - `sql_lineage_edges`
  - `code_lineage_edges`
- 当前更多是为 field mapping recall 服务

仍可继续增强：

- 增加按 definition / api_field_path / source_table / source_column 的查询接口
- 增加 lineage 资产的统计视图
- 增加审计字段或构建批次标识

目标：

- 支撑后续排查、分析、治理和报表

优先级：中

---

## P3：代码整理类事项

### 5. 继续压缩 `services.py` 的职责边界

当前状态：

- 已将上下文推导、decision trace、rule-only fallback 等重复逻辑收口成 helper
- 但 `FieldMappingAppService` 仍然承担较多编排与策略职责

仍可继续增强：

- 按阶段拆分更明确的 orchestrator / decision builder
- 把 AI decision policy 和 runtime verification merge policy 进一步外提
- 逐步把 `services.py` 控制在更清晰的编排边界内

目标：

- 降低后续继续演化时的复杂度

优先级：中低

---

## 当前结论

当前这套字段映射链路已经没有明显的“主流程未接线”问题，剩余事项主要集中在：

1. 把 lineage 自动抽取做得更深更稳
2. 把 lineage 资产构建做得更可运营
3. 继续做代码结构治理
