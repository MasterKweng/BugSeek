1）Controller 还没有真正瘦身，旧核心逻辑还挂在 API 层里

field_mappings.py 虽然 /field-mappings/suggest 已经接新 service 了，但这个文件里仍然保留着旧的：

_generate_mapping_candidates_with_gravity

_extract_api_fields

_extract_field_descriptions

一大堆旧 utils import

也就是说，控制器层仍然带着旧算法遗留物，没有真正清成“纯路由壳” 。

这会带来两个问题：

结构上仍然混乱

后续维护者无法明确“哪套才是主逻辑”

这一步没做干净，就不能说“系统级重构完成”。

2）旧核心没有真正退出系统，仍可通过 legacy runner 被调用

你现在不是“保留旧代码但彻底下线”，而是：

FieldMappingJobService._resolve_runner() 仍然会根据 engine_version 选择 LegacyFieldMappingJobRunner

LegacyFieldMappingJobRunner 仍然直接调用旧的 app.domains.data_mapping.processor.FieldMappingProcessor

这说明旧核心还在正式运行路径里，不是仅仅留作归档。

系统层面的标准不是“新东西加上了”，而是“旧核心已经从主系统退出”。
这一条现在还没做到。

3）AI 安全护栏在新引擎里明显回退了

这是我认为当前最严重的问题之一。

旧引擎虽然架构差，但至少在 AI 结果落地前，有：

物理列存在校验

域外软惩罚

hallucination fallback

而你现在的新 AIFieldMappingEnricher 只是把 AI 返回的 db_table/db_column 直接 merge 到候选里，并用更高分覆盖，没有看到任何：

_column_exists 校验

allowed_tables/domain 校验

hallucination reject/fallback

_merge_ai_candidates() 里就是直接吃 AI 候选并抬分 。
然后 FieldMappingAppService.optimize_ranked_items() 里又会在 ai_top >= rule_top 时直接让 AI 胜出 。

这意味着：

新引擎在 AI 可靠性上，反而比旧引擎更危险。

这条不修，不能验收。

4）trace 审计链没有真正闭环

你现在有：

field_mapping_traces 这张表模型资产还在系统里

但新引擎的 SuggestionWriter 只写了 FieldMappingSuggestion，没有写 trace

Celery _save_suggestions_to_db() 也只是委托给 SuggestionWriter，仍然没有 trace 落库

也就是说，新引擎虽然能产 suggestion，但证据审计没有真正持久化。

这会直接影响：

排错

误判追责

A/B 对比

人工审核回溯

如果没有 trace 闭环，这套系统还不能称为“高可靠”。

5）阶段工件有了，但 UI/状态解释层和新工件语义对不上

EngineV2FieldMappingJobRunner 现在写入的阶段摘要是这种结构：

stage1: input_snapshot

stage2: field_specs

stage3: recall_candidates

stage4: ai_ranked_items

stage5: final_suggestions

并且摘要里写的是 artifact_type / field_count / threshold / total_suggestions 这类字段 。

但是 field_mappings_async.py 里的 _calculate_stage_description() 还是按旧语义在解释阶段：

stage1 期待 total_fields / unique_fields / field_count_by_type

stage2 期待 processed_fields / success_fields / avg_score

stage3 期待 auto_confirm / ai_high / ai_medium / ai_low

stage4 期待 ai_optimized_fields / ai_failed_fields

这和新 runner 写进去的数据结构并不一致 。

所以现在你虽然有“新工件”，但控制台展示语义还是旧的，系统表面看能跑，实则观测层是错位的。

6）排序器仍然太“P1”，还没到“最终效果最好”的标准

CandidateRanker 现在本质上还是一个线性加权器，特征只有：

lexical

table similarity

history prior

comment similarity

exact match

vector similarity

runtime table/field hit

rule boosts

这能用，但还只是个简化版排序器 。

它还缺：

relation type classifier

confidence calibration

hard deterministic short-circuit 体系

stronger structural evidence

negative evidence / reject rules

field-position / sibling-context 深度利用

也就是说：

它已经比旧版健康很多，
但离“只看最终效果最好”的那套高可靠方案，还差一截。

7）输出仍然没有完成“关系类型 + 独立 confidence + 审计解释”的完整落地

现在 suggestion 输出的仍然主要是：

candidates

decision_trace

没有看到新引擎真正产出：

完整 relation_type 分类

独立 confidence calibration 结果

标准化 decision artifact

build_suggestions_from_ranked_items() 里输出的其实还是候选列表 + 简单 trace 摘要，不是完整裁决对象 。

这意味着：

它更像“新候选引擎”

还不是“完整裁决引擎”

8）还有明显的工程质量问题没有清干净

这里我直接点名：

A. 编码/乱码问题

field_mapping_tasks.py 和 field_mappings_async.py 里已经出现明显乱码字符串，说明编码链或文件处理还不稳定

B. 旧代码遗留 bug 还在文件里

field_mappings.py 里仍保留旧 helper 和旧 import，说明这次不是彻底替换，而是叠加式改造

这些问题单个不致命，但它们说明：

系统还没进入“可验收收口态”。
